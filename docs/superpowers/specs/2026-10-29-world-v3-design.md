# Agent Town 世界 v3 设计：主题小镇、2.5D 手绘建筑、技能公会

日期：2026-10-29 · 状态：待负责人批准 · 前置：`docs/decisions.md` D1–D14，`2026-10-28-world-v2-design.md`（第 1 步已完成）

本文**取代** v2 设计的第 2–4 步（代码街区、生活细节、视觉升级）。v2 第 1 步（真实数据、点击放大、任务日记、重放）保留并在本版继续使用。

## 1. 为什么改方向

负责人看了真实数据下的 v2 第 1 步和 KayKit 模型小样后的原话要点：

- 「目前的房子设计都很丑」，模型小样的房子「也都不好看」。
- 「如果一个小镇是一个 job 或者 skill，可以每一个小镇都设计的不同吗，而不是都长的一样」。
- 「每个房子的含义是什么」——现在看不出。
- 「工作的小人可以仔细设计下」，「如果需要，也可以使用 codex 来帮忙」。
- 更早：建筑名字「很奇异」；「所有过往的 job 都有显示，但很多是没什么用的」；技能（skill）应该融入世界。

本机实测（只统计数量，2026-10-29）：

| 事实 | 数 |
|---|---|
| 「任务」其实是对话轮次；其中系统开启的轮次（子代理交回、压缩续写等） | 3,129 轮，40% 系统开启 |
| 把系统轮次并回它所接续的人类请求后 | 1,871 个请求 |
| 改过文件或生成过图片的请求（有成品） | 697（37%） |
| 一次工具都没用的请求 | 15% |
| 只读/只跑命令的请求 | 30% |
| 现在的镇 | 104 个，其中真正的 git 仓库只有 19 个 |
| 产出最多的「镇」其实是技能目录 | `~/.codex/skills` 139 个有成品的请求，`~/.claude/skills` 90 个 |
| Claude 的 Skill 工具调用 | 101 次，技能名全部丢失（适配器没读 `input.skill`） |

## 2. 负责人已做的决定

| 决定 | 选择 |
|---|---|
| 建筑美术路线 | **2.5D**：每栋建筑由 Codex 按小镇主题生成一张等距图片，程序抠图后放进世界。视角固定，只能缩放和平移，不能旋转。 |
| 小人 | **KayKit Adventurers** 角色（CC0，3D，带 76 个动画），与建筑同一固定视角。 |
| 哪些任务进世界 | **有成品的请求 + 较大的调查**；问答只计数；空对话不显示；顶部开关「显示全部」。 |
| 公共建筑命名 | **直白的工作名**：读代码、改代码、跑命令、测试、联网、外部工具、计划、看图/生图、操作屏幕。镇名 = 仓库名；非项目文件夹 →「野外营地」。 |
| 技能 | 四项全要：公会大厅、小人佩戴公会徽章、用了技能的房子带公会样式、正在开发的技能 = 公会在施工。 |
| 含义体系 | 按第 5 节原样采用。 |
| 主题表 | 按第 6 节的初版，之后可手改。 |

## 3. 目标 / 非目标 / 反目标

**目标**
- G1 每个镇一眼不同：主题决定建筑样式，地标每镇独有，岛形和布局各不相同。
- G2 每个可见元素都有一句话说得清的含义（第 5 节），悬停即见。
- G3 世界里只有有用的工作；被省略的工作有计数，可一键显示。
- G4 技能是世界里的一等公民：有自己的公会镇，用到它的地方看得出来。
- G5 小人好看、动作可读：看动作就知道它在读、改、跑、等你、睡（压缩）、失败还是成功。
- G6 对任何用户的日志都成立：主题按规则自动分配，换一台机器、换一批项目也能得到合理的世界。

**非目标（这一版不做）**
- 视角旋转（负责人已接受固定视角）。
- 昼夜、天气、声音、小地图、事件流（留待以后）。
- v2 设计里的「文件地块」（一个文件一块地）：放弃；文件清单留在悬停卡和任务日记里。
- 实时监听（仍是「加载时读一次，可刷新」）。

**反目标（即使能跑也算失败）**
- 建筑或小人只是装饰、没有数据含义（D11.3 仍然有效）。
- 编造数字；缺数据时显示「—」。
- 日志内容离开本机：生成图片的提示词里**只有主题描述**，绝不出现项目名、文件名、对话内容。
- 两个镇长得一样（同主题的镇也必须靠地标、岛形、布局区分开）。
- 抠图留下品红色边、半截背景、或建筑被抠掉一块。
- M4 生产构建世界视图或镇视图低于 55 fps（p95 ≤ 20 ms）。

## 4. 数据：请求、成品、技能、归属

全部在服务端（`packages/server`）完成，前端只拿结果。

### 4.1 请求 = 人类开启的一轮 + 它的所有系统续轮
- 每个系统开启的轮次（`trigger: "system"`）并入同一会话里最近的一个人类开启的轮次，记 `requestId`。找不到人类轮次的系统轮次自成一个请求。
- 请求的 token、调用、失败、子代理、触及文件 = 所含各轮之和。
- 任务日记按请求展示，轮次作为分段（现有「接续：…」措辞保留）。

### 4.2 请求分类（每个请求恰好一类）
| 类 | 规则 | 世界里 |
|---|---|---|
| 成品 `produced` | 至少一次确切的改文件（Edit/Write/NotebookEdit/apply_patch）或一次生图工具调用 | 房子 |
| 调查 `investigation` | 不是成品，工具调用 ≥ 20 | 帐篷 |
| 问答 `chat` | 不是上两类，工具调用 ≥ 1 | 告示板计数 |
| 空 `empty` | 一次工具调用都没有 | 告示板计数（单列） |

阈值 20 放在配置里（`config/world.json`），测试覆盖边界 19/20。

### 4.3 成品种类（决定房子造型）
按这个请求**改过的文件**加权投票（每次改动一票），生图调用投「图片」：

| 种类 | 依据 |
|---|---|
| 代码 `code` | 源代码扩展名（ts/js/py/rs/go/java/c/cpp/sh/… 列表放配置） |
| 文档 `docs` | md/txt/rst/tex |
| 幻灯 `slides` | pptx/key，或路径含 `slides`/`deck` 且是 html/pdf |
| 图片 `image` | png/jpg/svg/webp/gif，或生图工具 |
| 影音 `video` | mp4/mov/mp3/wav/srt，或 remotion 合成源（路径含 `remotion`） |
| 数据 `data` | json/yaml/toml/csv/其它 |

平票取表中靠前者。没有扩展名的文件算 `code`。

### 4.4 技能识别
- **Claude**：`Skill` 工具的 `input.skill`（适配器补读这个字段，写进新字段 `skill`）；读 `…/skills/<name>/SKILL.md` 也算用到 `<name>`。
- **Codex**：命令或 apply_patch 路径里出现 `…/skills/<name>/SKILL.md`。
- 名字归一：去掉插件前缀（`superpowers:brainstorming` → `brainstorming` 保留前缀作显示副标题）、`_` 与 `-` 视为相同（`music_suggester` = `music-suggester`）。
- 每个请求记录用到的技能列表（按首次使用排序）。
- 技能描述：本机 `SKILL.md` 的 frontmatter `description` 首句，**只在本机页面显示**，不进提示词、不进 git。找不到文件就不显示描述。

### 4.5 归属：一个请求属于哪个镇
沿用 v2 的「按实际改动的文件投票」（D14：确切 > 推断 > cwd，家目录不投票），只换掉「票投给谁」：

1. 路径在 `<任意前缀>/skills/<name>/` 下 → **技能公会镇** `<name>`（Claude 与 Codex 各自一镇，与其它镇同样按阵营分）。
2. 路径在某个 git 仓库内 → 该仓库。**worktree 并回主仓库**（用 `git rev-parse --git-common-dir` 找主仓库）。
3. 路径在工具自己的目录下（`~/.claude/projects`、`~/.claude/plugins`、`~/.codex/sessions`、`~/.codex/generated_images` 等，列表放配置）→ 该阵营的**都城**里对应的区（「日志档案馆」「生图仓库」）。
4. 路径在一个有项目标记的目录下（`package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod`、`README*`，就近向上找、止于家目录）→ 该目录成镇。
5. 其它（`Downloads`、`Desktop`、按日期命名的临时目录、家目录本身…）→ 该阵营的**野外营地**。现有「临时工地」并入野外营地。

镇名：仓库/目录的名字；同名冲突时用 `父目录/名字`；技能公会镇显示 `<name> 公会`。

### 4.6 主题分配
- 规则表 `config/themes.json`：每个主题一组关键词，匹配**镇名 + 技能描述**（小写、分词）。第一个匹配的主题胜出；都不匹配 → 工匠镇。
- 本机覆盖：`~/.agent-town/themes.json`（`{ "<镇 key>": "<主题 id>" }`），不进 git。界面上悬停镇横幅可改主题（写这个文件）。
- 都城、野外营地有固定主题，不参与匹配。

### 4.7 下发给前端的摘要（`/api/world` 增量字段）
每个请求一行：`requestId, faction, town, startTs, endTs, ok, title, class, productKind, tokens(四项), calls, fails, spawns, skills[], topDir, turns`。
每个镇：`key, name, faction, kind(project|guild|capital|outpost), theme, counts{produced,investigation,chat,empty}, workCounts{读代码…: n}, lastEditTs`。
`topDir` = 该请求改动最多的一级目录（相对镇根），用于街道。

## 5. 世界里每样东西的含义

这张表同时是界面里「图例」的内容（首次进入的引导 + 悬停卡第一行）。

| 世界里 | 含义 | 由什么数据决定 |
|---|---|---|
| **岛（镇）** | 一个项目，或一个技能（公会镇） | 4.5 归属 |
| **岛的大小** | 镇里画了多少栋房子 | 房子数 |
| **地标** | 这个镇的身份建筑，每镇独有；随成品累积长 3 档 | 主题 + 成品数（档位阈值放配置：1 / 10 / 40） |
| **房子** | 一个有成品的请求 | 4.2 |
| 房子的造型 | 它主要产出了什么：代码/文档/幻灯/图片/影音/数据 | 4.3 |
| 房子的大小 | 工作量：这个请求的 token 在本镇的分位（小/中/大三档） | tokens |
| 门口的小旗 | 它用了哪个技能（公会颜色） | skills[0] |
| 屋顶灰、门口冒灰烟 | 这个请求以失败结束 | ok=false |
| **帐篷** | 一次较大的调查（只读，≥20 次工具调用） | 4.2 |
| **公共建筑** | 这个镇里发生过的一类工作；小人去那里干活；用得越多越大（3 档） | workCounts；没发生过的不建 |
| **告示板** | 问答与空对话的次数 | counts |
| **街道** | 一级目录；房子建在它改动最多的那条街上 | topDir（每镇最多 6 条，其余并入「其他」） |
| **脚手架工地** | 进行中的请求（v2 的判定不变） | live |
| **公会大厅脚手架** | 这个技能的文件最近 7 天被改过 = 技能在开发中 | 公会镇 lastEditTs |
| **桥** | 两阵营在 30 分钟内碰了同一个项目（推断，沿用 v1） | 不变 |

## 7. 美术管线（Codex 生成 → 抠图 → 质检 → 入库）

### 7.1 生成
- 脚本 `scripts/art/generate.ts`（或 Python，见第 11 节），读 `art/catalog.json`（每张图：id、主题、类别、提示词），只生成缺的。
- 走 **Codex 订阅**（`codex exec` + 托管生图工具），不用 API key。先检查当前 Codex 账号能否生图（读最新 rollout 的 plan_type / 试生成一张），不能就停下并说明原因。
- 提示词模板统一：同一风格段（暖陶玩具镇：哑光彩泥、圆角、左上暖光、柔和 AO）、同一视角段（严格 2:1 等距，从东南方看，30° 仰角，整栋居中留边，站在一小块石板地基上）、纯品红 `#FF00FF` 背景、无文字无 logo、正方形。只有「建筑描述」一段随条目变化。
- 提示词里只有主题和建筑描述。**禁止**出现项目名、路径、对话内容（脚本断言：提示词不含任何本机镇名）。

### 7.2 抠图与质检（每张图自动跑）
- 品红色键控：只去掉**与图像边缘连通**的品红区域（建筑内部的紫红细节保留），边缘软化并去色溢出；裁到内容加 4 px 边。
- 质检，任一不过就标记重生成，不入库：
  - 边缘一圈像素必须全透明（背景没抠干净）。
  - 保留像素占比在 15%–85%（防止整张被抠掉或背景没去掉）。
  - 不透明区域里品红色调像素 < 0.5%（防残边）。
  - 地基底边可检测：底部轮廓左右两段斜率与 2:1 等距相差 ±15% 以内（防视角跑偏）。
  - 宽高比在 0.6–1.6。
- 入库：缩到最长边 512 px，WebP（带 alpha），存 `packages/web/public/art/<theme>/<id>.webp`，另存一份 128 px 缩略图做远景/图集。`art/manifest.json` 记录每张图的尺寸、地基锚点（底边中点，像素坐标）、来源提示词哈希。原始大图放 `~/.agent-town/art-src/`，不进 git。
- 每批生成后输出一张总览拼图到 `~/Desktop/agent-town-美术/<批次>.png`，给负责人过目。

### 7.3 每镇不同的地标
- 每个主题在目录里列 6 个地标创意（例：影视镇 = 圆顶影院 / 摄影棚 / 露天剧场 / 胶片塔 / 录音钟楼 / 放映船）。
- 本机同主题有 N 个镇时，按镇的稳定哈希分配互不相同的创意；超过 6 个时再按「创意 × 配色变体」区分，配色变体由生成时的提示词决定（例：屋顶陶红/石板蓝/苔绿），不是前端染色。
- 每个创意生成 3 档（小/中/大）。
- 地标只按主题和创意编号生成，不带项目名；所以同一套美术对任何用户都能复用。

### 7.4 数量与入库
- 预计：9 个主题 ×（6 地标 × 3 档 + 6 种房子 × 2 变体）= 270 张，加共用 12 座公共建筑 × 2 阵营配色 × 3 档 = 72 张，加帐篷、告示板、脚手架 3 档、都城大厅 ×2、营地、道具约 15 张 ≈ 360 张。
- **分批**：第一批只做出版镇 + 影视镇 + 工匠镇 + 共用建筑（≈ 150 张），负责人看过总览再做其余。
- 入库体积目标：512 px WebP 约 60–100 KB/张 → 全部 ≤ 40 MB；只在需要时按镇加载（见 8.4）。

## 8. 世界的呈现

### 8.1 视角
- 正交相机固定方位角 45°（从东南看）、仰角 30°，与生成图一致。缩放、平移保留，旋转关闭。
- 远景：看整片群岛；近景：一栋房子占屏幕约 1/4 高时仍清晰（2× 屏）。

### 8.2 群岛布局
- 每个镇是一座岛：六边形格子的并集，格子数按房子 + 公共建筑 + 地标所需决定，形状由镇 key 的哈希生长（稳定：同样输入同样形状；镇里加一栋房子不重排已有房子）。
- 岛体 = 3D：草顶（细噪声纹理，非纯色）+ 岩石崖壁 + 岸边浅水泡沫环。颜色与生成图的暖陶色调对齐。
- Claude 群岛在西，Codex 群岛在东，中间一条海峡；每阵营都城在靠海峡的中央，公会镇围在都城周围（「公会区」），项目镇往外，野外营地在最外缘。
- 桥（跨阵营协作）横跨海峡，沿用 v1 规则。

### 8.3 镇内布局
- 中心小广场：地标 + 任务大厅 + 告示板。
- 公共建筑围在广场外一圈，只建发生过的。
- 街道从广场放射（每条 = 一级目录，最多 6 条），房子沿街排，按完成时间依次追加。
- 帐篷在岛边缘。
- 装饰（树、灯、木桶、花）只放在空格子上，密度适中；装饰也是生成图（与建筑同一风格），不用 KayKit 模型。

### 8.4 精灵绘制
- 每栋建筑 = 一个竖直、正对相机的四边形，底边中点贴在地面锚点上；alpha 测试写深度，以便小人能正确地走到房子前后。
- 同一张图集里的精灵用实例化绘制；远景用 128 px 缩略图集，近景按需换 512 px。
- 每个精灵下面画一块软阴影贴花，让它「站」在地上。
- 3D 部分（岛、小人、水）的主光方向与生成图的光一致（屏幕左上方来光）。

### 8.5 标签

## 13. 实现前已定的细节（审阅后补充，均为「我的决定」，负责人可推翻）

1. **Codex 生图可用性与预算**：2026-10-29 已实测 Codex 订阅可生图（4 张，2 路并发约 1 分钟/张）。生成脚本先试生成 1 张；不能生图就停下、说明原因，**不**改用付费 API。每张图自动质检不过最多重生成 2 次，仍不过就列进总览拼图的「待你看」区，由负责人决定。风格一致性靠统一的提示词模板 + 质检 + 总览人工过目，不做参考图。
2. **同主题镇多于 6 个**：6 个创意 × 2 套配色（提示词里写定的屋顶/墙面配色）= 12 个不同地标；超过 12 个时按需为该主题追加创意并生成。
3. **成品种类跨主题一眼可辨**：每种成品房子门口有同一种**挂牌道具**（代码 = 齿轮牌、文档 = 卷轴牌、幻灯 = 画架、图片 = 画框、影音 = 胶片盘、数据 = 木箱堆），写进每个主题的房子提示词；房子本体随主题变化。悬停卡写明种类。
4. **请求取代任务成为世界单位**：`/api/world`、选中键（`#req=<id>`）、悬停卡、日记都按请求；轮次只作日记里的分段。旧的 `#task=<轮次 id>` 链接自动转到它所属的请求。D5 对账不变（按事件求和，与分组无关）；另加一条测试：所有请求的 token 之和 = 所有轮次之和。
5. **技能与仓库重叠**：技能目录若在某个 git 仓库里（如 `slides_maker` 仓库里的 `skills/slide-maker`），**这个仓库镇就是该技能的公会镇**——一个镇，镇名用仓库名，横幅加「slide-maker 公会」副标题，主题按技能定。不在仓库里的技能目录（`~/.claude/skills/<name>`）自成公会镇。一个请求同时改了多个镇的文件时按票数，平票按第 4.5 节规则顺序。每个阵营各自一个公会镇，两阵营同名公会的横幅互相标出。`lastEditTs` 用日志里改文件事件的时间戳，不读文件 mtime。
6. **没有美术的主题**：回落到工匠镇美术（所以第一批包含工匠镇）；地标回落到工匠镇的地标。v1/v2 的程序化建筑删除，不保留。精灵是竖直、正对相机的四边形；小人走到高地标后面时由深度测试遮挡，边缘处的小误差可以接受。
7. **美术入 git**：512 px 与 128 px 的 WebP、`art/catalog.json`、`art/manifest.json` 都提交（本地，不推送）；原始大图不进 git。别的用户直接用仓库里的美术，不必生成。
8. **改主题的写接口**：`POST /api/theme`，沿用现有 Host/Origin 检查，只接受已知镇 key 与已知主题 id，写 `~/.agent-town/themes.json`。
9. **KayKit 资源**：Adventurers 包（CC0）放进 `packages/web/public/figures/`，附原 LICENSE；包里有斧、弩、法杖、打开/合上的书、盾，没有锤子——改代码用斧。只保留用到的动画、压缩网格以控制体积。
